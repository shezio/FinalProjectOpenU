What we will implement

F7FixPrivate storage + short-lived signed links
DoSet the receipts and financial-aid containers to private; serve each file via a short-lived (~1h) signed read link generated on read. Trade-off accepted: links become time-limited. The "open in a new tab" experience is unchanged — a signed link opens with no login, and the swap from public URL to signed link happens on the server, so no frontend change.
OrderDeploy the signed-link code first, flip the containers to private last (so no in-app link breaks in the gap). Also delete the leftover PoC marker blob.
F8FixUpload file-type allow-list
DoRestrict receipt/document uploads to pdf / jpg / png; reject anything else before a link is issued, and mark stored files as attachments so active content can't be served inline.
F9FixFrontend security headers (+ report-only CSP)
DoAdd X-Frame-Options: DENY + X-Content-Type-Options: nosniff to the web app (verified: no effect on TOTP or Google sign-in — no iframes, sign-in is a full-page redirect). Add a Content-Security-Policy in report-only mode as the defense-in-depth layer — it enforces nothing, only reports, so it can't break anything; enforce later once proven clean.
F10FixRoles-distribution report error
DoFix the report's database query so the page loads again. Plain bug, no data exposure.
F13FixImmediate offboarding
DoOn disabling a user, immediately end that specific user's active session(s) so access is revoked on the spot — scoped strictly to that one user, no effect on anyone active. Login is already blocked for disabled users; we'll re-verify that's live in production.
F17FixPublic voucher form — field whitelist
DoOn the public voucher form, accept only the fields a family is meant to fill and ignore any admin-only fields (approved amount, "ready", "delivered", status) if injected — matching the protection the activity form already has.
F12FixEnforce read authorization — with data-minimization
DoAdd the missing resource:VIEW permission checks to the PII read endpoints, so enforcement exists on every read — a role or account without the permission (e.g. a deactivated account) is blocked.
MinimizeA permission audit showed only the Reviewer role lacked the needed views. We grant it staff-directory VIEW only (names/phones/roles — no national-IDs) and not the tutor/pending-tutor endpoints. Verified against its screen: the Reviewer page never calls those endpoints, so it keeps working while being blocked from tutor national-IDs entirely — the minimizing outcome, with no names-only endpoint needed.
F11FixViewer guard — mechanically enforced
AgreedThe reviewer's point is accepted: a "remember to add the guard" fix for a "forgot the guard" bug is circular — the check must be mechanical, not a convention.
DoAdd a static guard-coverage check (plain text/AST parsing — no framework boot, no database, runs in seconds) that scans for any state-changing endpoint missing the @block_viewer_writes guard. It runs as a gate in the deploy pipeline: if a guard is ever missing, the deploy is stopped before it publishes — production keeps serving the current version and the build simply reports failed.
Why this formIt's a guarantee, not a reminder, so it closes the exact "future endpoint ships without the guard" risk — while, deliberately, never running inside the live application, so it can't cause a runtime outage. The Viewer keeps its identical read-only admin experience.

Accepted — no action — deliberate, with reasons

F5AcceptCSRF token not enforced server-side
WhyThe session cookie is SameSite=Lax, which browsers use to block the cross-site vector; with the F9 report-only CSP added as a second layer, server-side token enforcement is low value and carries real breakage risk.
F14AcceptAny staff can submit a refund
WhyBy design — anyone may request reimbursement for money they spent. Confirmed in code that approving / setting the amount / marking paid is administrators-only, so a staff member cannot approve or pay their own refund (segregation of duties holds).
F15 / F16AcceptPublic questionnaire id & existence
WhyThe questionnaires are intentionally open to the public; there are no invite-only rounds, so a simple id grants no extra access and there is nothing to conceal. The reviewer confirmed no personal data is exposed and submitted responses are never publicly readable.
