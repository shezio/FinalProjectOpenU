A Child's Smile · Security Architecture Document

Moving from Table-Based Permissions to Stateless Authorization

JWT, PASETO and more-secure alternatives — an honest analysis, OWASP mapping, and a phased recommendation
For: Liam Avivi (security expert) Written: 2026-07-26 Status: Proposal for discussion System version: Backend 26.07.12.x

Bottom line (TL;DR)

A "naive" move to a long-lived JWT stored in localStorage would be a security downgrade, not an upgrade — it loses exactly the two properties we already rely on today: instant revocation and fresh authorization, and it adds a token-theft attack surface plus the classic cryptographic footguns of JWT.

The recommendation therefore has two tracks:

  • Primary recommendation  Solve the real problem (DB load) without changing the trust model — keep server-side sessions, add a permissions cache layer, and add a security_version for instant revocation. More secure than JWT, and less work.
  • Future option  If we genuinely need stateless tokens (mobile app / external API / horizontal scale) — a hardened PASETO-based hybrid (preferred over raw JWT) with a short-lived access token + rotating refresh token + kill-switch. Restores revocation while keeping statelessness.

Every conclusion in this document is mapped to the OWASP Top 10 (2021) and the relevant cheat sheets.

1Current state — what we already have

Before replacing anything, it's important to describe precisely what exists — because the current baseline is stronger than people tend to assume:

  • Passwordless login (TOTP): a one-time code sent to email, with no stored passwords at all — a built-in security advantage.
  • Server-side sessions backed by the DB: after verification an opaque sessionid is issued in a cookie; the state itself lives in the django_session table. Expiry is extended to 24 hours (set_expiry(86400)).
  • Single-device enforcement: on every login, logout_all_other_sessions() deletes all of the user's other sessions — meaning we already rely on instant server-side revocation.
  • Hardened cookie: HttpOnly, Secure, SameSite=Lax (in prod), with the Domain scoped to .achildssmile.org.il.
  • Permissions model: role / permissions / staff_roles tables. At login the permission list is loaded in a single JOIN into session["permissions"], and has_permission(request, resource, action) reads from it (no DB hit).
The real pain point — performance, not security

has_permission() does read from the session, but is_admin() and is_viewer_user() perform a DB query on every request/write, and loading the session itself is a DB read. This is the "tax" that motivates the move to tokens — and it's a load problem, solvable without giving up any security properties.

2Which problem are we actually solving?

"Move to JWT" conflates three separate goals. Separating them matters, because each has a different solution:

Performance / load

Reduce per-request DB queries. Solvable with cache — no tokens needed

Statelessness / scale

Auth with no shared state, for multi-instance / mobile / API. Requires tokens

Developer experience

A token that carries permissions "built in". Nice — but brings risk with it

Security

Here server-side sessions are actually superior to naive JWT on most axes.

For an NPO app with a single SPA, the realistic goal today is performance — so the most secure solution is not necessarily tokens.

3Why naive JWT is a security downgrade

These are all well-known weaknesses of a long-lived, permission-carrying JWT. A security expert will spot them immediately:

3.1 · No instant revocation — A01 / A07

A signed token is valid until it expires. If a token is stolen, if an employee is offboarded, or if we need to "kick everyone out" — you cannot revoke it without adding a server-side blocklist, which is… server-side state again. We already rely on instant revocation (single-device); moving to naive JWT breaks an existing capability.

3.2 · Stale authorization — A01 Broken Access Control

If permissions are "baked" into the token, a role change (removing a coordinator, promotion/demotion, switching to Viewer) won't take effect until the token expires. In a fully permission-driven system (coordinators with cross-domain grants, read-only Viewer, Reviewer) — that's a real access-control failure.

3.3 · Classic JWT cryptographic footguns — A02 Cryptographic Failures
  • alg:none — an "unsigned" token accepted by mistake.
  • Algorithm confusion — tricking a server that expects RS256 into verifying HS256 using the public key as the "secret".
  • Weak secret — HS256 with a short/guessable secret → offline key cracking → token forgery.
  • Key management — one leaked signing key = account takeover across all users until rotation.
3.4 · The client-side storage dilemma — A03 (XSS)

localStorage is accessible to JavaScript ⇒ any XSS steals the token. An HttpOnly cookie solves XSS but then you're back to needing CSRF protection — so the "statelessness benefit" evaporates. Today our sessionid is already HttpOnly, and localStorage.permissions is used only as a UI hint, never as a source of authority.

4Recommendation A — Sessions + Cache + security_version Primary

Keep the strong existing trust model, and attack only the load problem:

  1. Permissions cache layer: move is_admin/is_viewer/the permission list into a cache keyed by staff id (perms:{staff_id}) with a short TTL (say 60 seconds) or explicit eviction on role change. Hit the DB only on a miss.
  2. A security_version column on Staff: an integer bumped on any role/permission change or "log me out of all devices". It's stored in the session; a mismatch forces an immediate refresh of the permissions (staleness ≈ 0).
  3. Cache for sessions: a cached_db session backend (Redis + DB fallback) removes the per-request DB read without losing durability or instant revocation.
Why this is more secure than JWT

It preserves instant revocation, fresh permissions, single-device, and HttpOnly storage — while eliminating the DB cost that is the actual motivation. No signing keys, no alg, no token stored in JS. The attack surface shrinks, not grows.

New dependency

Redis (or the existing Django cache). cryptography and channels are already installed; Redis is the only addition, and it usually already exists as infrastructure.

5Recommendation B — Hardened hybrid (PASETO / JWT) If stateless is genuinely required

If we later add a mobile app, a third-party API, or true multi-instance scale — this is the right way to do tokens without falling into the traps of section 3:

5.1 · Two tokens, not one

  • Short-lived access token (5–10 min): carries sub, roles, and sv (security_version). Prefer carrying roles only and mapping role→permissions on the server, to avoid leaking the whole permission matrix and to keep the token small. Verified without a DB.
  • Opaque refresh token: random, stored hashed on the server, in an HttpOnly + Secure + SameSite=Strict cookie. This is what enables revocation.

5.2 · Rotation + reuse detection

Every use of the refresh token issues a new one and invalidates the old. If an already-used refresh token is presented — that's a theft signal ⇒ revoke the entire token "family" for that user. This restores kill-switch semantics.

5.3 · Kill-switch via security_version

The access token carries sv; the server compares it to a per-user integer held in cache. A role change or "log everyone out" increments that integer ⇒ all existing access tokens are rejected immediately. It's a single-integer lookup (cacheable) — so you keep statelessness for 99% of requests while gaining near-instant revocation. The staleness window is bounded by the TTL (minutes).

5.4 · Prefer PASETO over raw JWT "better than JWT"

PASETO (Platform-Agnostic Security Tokens)

PASETO v4.public (Ed25519) eliminates by design the entire family of JWT attacks: no algorithm negotiation, no alg:none, no algorithm confusion, no weak-cipher selection. Each version has one hard-coded algorithm. This is the precise answer to "do something more secure than JWT."

If we still stay with JWT (for ecosystem reasons) — it's mandatory to: use a hard algorithm allow-list, reject none, use an asymmetric algorithm (EdDSA/ES256), validate iss/aud/exp/nbf, and use kid-based key rotation. Note: a jwt library already exists in requirements — verify it's a maintained one (e.g. PyJWT) before relying on it.

5.5 · Client-side storage

Never store the access token in localStorage. Keep it in memory only (a JS variable), and rely on the refresh cookie (HttpOnly) to re-mint it on reload. This closes the XSS-exfiltration path.

Advanced hardening (optional)

Sender-constrained tokens (DPoP, RFC 9449) or mTLS — bind the token to the client's key, so a stolen access token cannot be replayed from another device.

8Phased migration plan (each step reversible and valuable on its own)

Phase 0
Cache is_admin/is_viewer + add security_version. Immediate performance gain, minimal change.
Phase 1
Cache-backed session backend (Redis) + permission eviction on role change. Completes "Recommendation A".
Phase 2
Only if stateless is required: a PASETO hybrid (access+refresh, rotation, kill-switch) alongside the existing session.
Risk strategy

Stop after Phase 1 for today's needs. Phase 2 only enters when there's a justified trigger (mobile/API). No "big-bang", no risky replacement of the entire auth mechanism at once.

9What not to do (anti-patterns)

Disqualification list
  • Do not store an access/JWT in localStorage or sessionStorage.
  • Do not use HS256 with a short secret; do not accept the alg from the token without an allow-list; reject none.
  • No long-lived (hours/days) access tokens without a revocation mechanism.
  • Do not bake the entire permission matrix into a client-visible token.
  • Do not rely on client-side localStorage.permissions as a source of authority — it's a UI hint only; the authoritative check must stay on the server.

10Illustrative code snippets

For illustration only — not production code. Demonstrates principles, not a final implementation.

10.1 · Hardened JWT verification (if JWT is chosen over PASETO)

# hard allow-list, reject none, validate aud/iss, asymmetric algorithm only
import jwt
def verify_access(token, public_key):
    return jwt.decode(
        token, public_key,
        algorithms=["EdDSA"],        # EdDSA only — no HS*, no none
        audience="childsmile-app",
        issuer="childsmile-auth",
        options={"require": ["exp", "iat", "sub", "sv"]},
    )

10.2 · Kill-switch via security_version

# one integer in cache; a mismatch = immediate rejection of all old tokens
def is_token_current(claims):
    current_sv = cache.get(f"sv:{claims['sub']}")
    if current_sv is None:
        current_sv = Staff.objects.only("security_version") \
                        .get(pk=claims["sub"]).security_version
        cache.set(f"sv:{claims['sub']}", current_sv, 300)
    return claims["sv"] == current_sv   # bump in DB ⇒ instant invalidation

10.3 · Recommendation A — permission cache (the minimal, recommended step)

# removes the per-request DB query, no tokens and no loss of instant revocation
def get_perms_cached(staff_id):
    key = f"perms:{staff_id}"
    perms = cache.get(key)
    if perms is None:
        perms = load_perms_from_db(staff_id)   # the existing JOIN
        cache.set(key, perms, 60)             # short TTL or evict on role change
    return perms

11Future horizon — going "beyond JWT" at the architecture level

Since I was asked to "go wild" — here are the advanced directions beyond tokens per se, in case the permission matrix keeps growing (coordinators, Viewer, Reviewer, cross-domain grants):

Policy-as-Code

OPA/Rego or Cedar (AWS) move authorization decisions out of application code into a dedicated, testable, auditable policy engine. A good fit for a system where "who may do what" is branching out.

Capability tokens

Biscuit / Macaroons — capability-based tokens you can "attenuate" with caveats and verify offline. Powerful for fine-grained delegation, but overkill for today.

Note

These are beyond the current scope — presented to show the full solution space. None are needed to solve the load problem.

12Open questions for Liam (decisions that need a security judgment)

  1. Is a non-browser client (mobile / third-party API) expected in the foreseeable future that genuinely justifies stateless tokens? If not — Recommendation A is sufficient.
  2. What is the acceptable staleness window for permissions? (0 = sessions/cache required; a few minutes = a hybrid is legitimate.)
  3. Is Redis available/acceptable as prod infrastructure (Azure)? It's the only dependency of Recommendation A.
  4. If we go with tokens — PASETO (recommended) or a hardened asymmetric JWT? Where would the signing keys live (Key Vault) and under what rotation policy?
  5. Should we adopt DPoP / sender-constraining against replay, or does the risk not justify the complexity?
