מעבר ממודל הרשאות מבוסס־טבלאות ל־Stateless Authorization

JWT, PASETO וחלופות מאובטחות יותר — ניתוח כן, מיפוי ל־OWASP והמלצה מדורגת
מיועד ל: ליאם אביבי (מומחה אבטחה) נכתב: 26.07.2026 סטטוס: הצעה לדיון גרסת מערכת: Backend 26.07.12.x

שורה תחתונה (TL;DR)

מעבר "תמים" ל־JWT ארוך־טווח שמאוחסן ב־localStorage יהיה הורדה באבטחה, לא שדרוג — הוא יאבד בדיוק את שתי התכונות שאנחנו כבר נשענים עליהן היום: ביטול מיידי (revocation) ו־טריות הרשאות (fresh authorization), ויוסיף משטח תקיפה של גניבת אסימון ותקלות קריפטו קלאסיות של JWT.

לכן ההמלצה בשני צירים:

  • מומלץ ראשי  לפתור את הבעיה האמיתית (עומס DB) בלי לשנות את מודל האמון — להשאיר Sessions צד־שרת, להוסיף שכבת Cache להרשאות, ולהוסיף security_version לביטול מיידי. יותר מאובטח מ־JWT, פחות עבודה.
  • אופציה עתידית  אם באמת נצטרך אסימונים חסרי־מצב (אפליקציית מובייל / API חיצוני / scale אופקי) — Hybrid מוקשח מבוסס PASETO (עדיף על JWT גולמי) עם access קצר־טווח + refresh מסתובב + kill-switch. משחזר את הביטול תוך שמירה על statelessness.

כל מסקנה במסמך ממופה ל־OWASP Top 10 (2021) ולמסמכי ה־Cheat Sheet הרלוונטיים.

1המצב הנוכחי — מה כבר יש לנו

לפני שמחליפים, חשוב לתאר במדויק מה קיים, כי הבסיס הנוכחי חזק יותר ממה שנהוג לחשוב:

  • כניסה ללא סיסמה (Passwordless TOTP): קוד חד־פעמי לאימייל, אין סיסמאות מאוחסנות כלל — יתרון אבטחה מובנה.
  • Sessions צד־שרת מגובות ב־DB: לאחר אימות נוצר sessionid אטום בעוגייה; המצב עצמו נשמר בטבלת django_session. תוקף מוארך ל־24 שעות (set_expiry(86400)).
  • אכיפת מכשיר יחיד: בכל התחברות logout_all_other_sessions() מוחק את כל שאר ה־sessions של המשתמש — כלומר אנחנו כבר נשענים על ביטול מיידי צד־שרת.
  • עוגייה מוקשחת: HttpOnly, Secure, SameSite=Lax (בפרוד), Domain מוגבל ל־.achildssmile.org.il.
  • מודל הרשאות: טבלאות role / permissions / staff_roles. בכניסה נטענת רשימת ההרשאות ב־JOIN אחד אל session["permissions"], ו־has_permission(request, resource, action) קורא ממנה (ללא פנייה ל־DB).
נקודת הכאב האמיתית — ביצועים, לא אבטחה

has_permission() אמנם קורא מה־session, אבל is_admin() ו־is_viewer_user() מבצעים פנייה ל־DB בכל בקשה/כתיבה, וגם טעינת ה־session עצמה היא קריאת DB. זהו ה"מס" שמניע את הרצון לעבור לאסימונים — וזו בעיית עומס, שאפשר לפתור בלי לוותר על תכונות האבטחה.

2איזו בעיה אנחנו באמת פותרים?

"מעבר ל־JWT" מערבב שלוש מטרות נפרדות. חשוב להפריד ביניהן כי לכל אחת פתרון אחר:

ביצועים / עומס

להוריד פניות DB לכל בקשה. פתיר עם Cache — ללא אסימונים

Statelessness / Scale

אימות בלי מצב משותף, לריבוי מכונות / מובייל / API. מצריך אסימונים

חוויית מפתח

אסימון שנושא הרשאות "מובנה". נחמד — אך מביא איתו סיכונים

אבטחה

כאן דווקא Sessions צד־שרת עדיפים ברוב הפרמטרים על JWT תמים.

עבור אפליקציה של עמותה עם SPA יחיד, המטרה הריאלית היום היא ביצועים — ולכן הפתרון המאובטח ביותר הוא לא בהכרח אסימונים.

3למה JWT "תמים" הוא הורדה באבטחה

כל אלה הן חולשות מוכרות של JWT ארוך־טווח נושא־הרשאות. מומחה אבטחה יזהה אותן מיד:

3.1 · אין ביטול מיידי (No Revocation) — A01 / A07

אסימון שנחתם תקף עד לפקיעתו. אם אסימון נגנב, אם עובד מסיים העסקה, או אם צריך "לנתק את כולם" — אי אפשר לבטל בלי להוסיף בחזרה רשימת שלילה צד־שרת (blocklist), שזה כבר… מצב צד־שרת. אנחנו כבר נשענים על ביטול מיידי (מכשיר יחיד) — מעבר ל־JWT תמים שובר יכולת קיימת.

3.2 · הרשאות מתיישנות (Stale Authorization) — A01 Broken Access Control

אם ההרשאות "צרובות" בתוך האסימון, שינוי תפקיד (הסרת רכז, שדרוג/שנמוך, מעבר ל־Viewer) לא ייכנס לתוקף עד שהאסימון יפקע. במערכת שכולה מונעת־הרשאות (רכזים עם הרשאות חוצות־תחום, Viewer לקריאה־בלבד, Reviewer) — זה כשל בקרת גישה ממשי.

3.3 · תקלות קריפטוגרפיות קלאסיות של JWT — A02 Cryptographic Failures
  • alg:none — אסימון "לא חתום" שמתקבל בטעות.
  • Algorithm confusion — הטעיית שרת שמצפה ל־RS256 לאמת HS256 עם המפתח הציבורי כ"סוד".
  • Weak secret — HS256 עם סוד קצר/צפוי → כריית מפתח לא־מקוונת → זיוף אסימונים.
  • ניהול מפתחות — דליפת מפתח חתימה אחד = השתלטות על כל המשתמשים עד לרוטציה.
3.4 · דילמת האחסון בצד־לקוח — A03 (XSS)

localStorage נגיש ל־JavaScript ⇒ כל XSS גונב את האסימון. עוגייה HttpOnly פותרת XSS אבל אז חוזרים לצורך בהגנת CSRF — כלומר "יתרון ה־statelessness" מתאדה. היום ה־sessionid שלנו כבר HttpOnly, וה־localStorage.permissions משמש רק כרמז UI ולא כמקור סמכות.

4המלצה א' — Sessions + Cache + security_version מומלץ ראשי

לשמור על מודל האמון החזק הקיים, ולתקוף רק את בעיית העומס:

  1. שכבת Cache להרשאות: להעביר את is_admin/is_viewer/רשימת ההרשאות ל־Cache לפי מזהה עובד (perms:{staff_id}) עם TTL קצר (למשל 60 שניות) או פינוי מפורש בעת שינוי תפקיד. פנייה ל־DB רק ב־miss.
  2. עמודת security_version על Staff: מספר שלם שמוגדל בכל שינוי תפקיד/הרשאה או "נתק אותי מכל המכשירים". הוא נשמר ב־session; אי־התאמה מאלצת רענון מיידי של ההרשאות (staleness ≈ 0).
  3. Cache ל־sessions: cached_db session backend (Redis + גיבוי DB) מוריד את קריאת ה־DB לכל בקשה, בלי לאבד עמידות או ביטול מיידי.
למה זה יותר מאובטח מ־JWT

שומר ביטול מיידי, הרשאות טריות, מכשיר יחיד ו־אחסון HttpOnly — ומבטל את עלות ה־DB שהיא המניע האמיתי. אין מפתחות חתימה, אין alg, אין אחסון אסימון ב־JS. משטח התקיפה קטֵן, לא גדל.

תלות חדשה

Redis (או Django cache קיים). cryptography ו־channels כבר מותקנים; Redis הוא התוספת היחידה, ולרוב כבר קיים כתשתית.

5המלצה ב' — Hybrid מוקשח (PASETO / JWT) אם באמת צריך Stateless

אם בעתיד נוסיף אפליקציית מובייל, API לצד־שלישי, או ריבוי מכונות אמיתי — זו הדרך הנכונה לעשות אסימונים בלי ליפול למלכודות של פרק 3:

5.1 · שני אסימונים, לא אחד

  • Access token קצר־טווח (5–10 דק'): נושא sub, roles ו־sv (security_version). מומלץ לשאת תפקידים בלבד ולמפות תפקיד→הרשאות בשרת, כדי לא לדלוף את כל מטריצת ההרשאות ולשמור על אסימון קטן. אימות ללא DB.
  • Refresh token אטום (opaque): אקראי, נשמר בשרת מגובב (hashed), בעוגיית HttpOnly + Secure + SameSite=Strict. הוא זה שמאפשר ביטול.

5.2 · רוטציה + זיהוי שימוש חוזר (Refresh Rotation & Reuse Detection)

כל שימוש ב־refresh מנפיק חדש ומבטל את הקודם. אם מוצג refresh שכבר נוצל — זהו איתות גניבה ⇒ ביטול כל "המשפחה" של האסימונים למשתמש. זה משחזר את סמנטיקת ה"kill switch".

5.3 · Kill-switch דרך security_version

ה־access נושא sv; השרת משווה למספר per-user שנשמר ב־Cache. שינוי תפקיד או "נתק הכל" מגדיל את המספר ⇒ כל ה־access tokens הקיימים נדחים מיד. בדיקה של מספר שלם אחד (ניתן ל־Cache) — כך שומרים statelessness ל־99% מהבקשות אך מקבלים ביטול כמעט־מיידי. חלון ה־staleness חסום ל־TTL (דקות).

5.4 · עדיף PASETO על JWT גולמי "טוב יותר מ־JWT"

PASETO (Platform-Agnostic Security Tokens)

PASETO v4.public (Ed25519) מבטל בתכנון את כל משפחת ההתקפות של JWT: אין משא־ומתן על אלגוריתם, אין alg:none, אין algorithm confusion, אין בחירת ספרים חלשים. לכל גרסה אלגוריתם קשיח אחד. זו התשובה המדויקת ל"תעשה משהו מאובטח יותר מ־JWT".

אם בכל זאת נשארים עם JWT (בשל אקוסיסטם) — חובה: allow-list קשיח לאלגוריתמים, דחיית none, אלגוריתם א־סימטרי (EdDSA/ES256), אימות iss/aud/exp/nbf, ורוטציית מפתחות מבוססת kid. שימו לב: ב־requirements קיימת ספריית jwt — יש לוודא שמדובר בספרייה מתוחזקת (למשל PyJWT) לפני הישענות עליה.

5.5 · אחסון בצד־לקוח

לעולם לא לשמור access token ב־localStorage. להחזיק אותו בזיכרון בלבד (משתנה JS), ולהסתמך על עוגיית ה־refresh (HttpOnly) כדי לחדש אותו בטעינה מחדש. זה חוסם את נתיב הדליפה דרך XSS.

הקשחה מתקדמת (רשות)

אסימונים כבולי־שולח (DPoP, RFC 9449) או mTLS — כובלים את האסימון למפתח של הלקוח, כך שאסימון גנוב לא ניתן לשימוש חוזר ממכשיר אחר.

8תוכנית מעבר מדורגת (כל שלב הפיך ובעל ערך בפני עצמו)

שלב 0
Cache ל־is_admin/is_viewer + הוספת security_version. רווח ביצועים מיידי, שינוי מינימלי.
שלב 1
Session backend מבוסס־Cache (Redis) + פינוי הרשאות בעת שינוי תפקיד. מסיים את "המלצה א'".
שלב 2
רק אם יידרש Stateless: Hybrid PASETO (access+refresh, רוטציה, kill-switch) לצד ה־session הקיים.
אסטרטגיית סיכון

לעצור אחרי שלב 1 עבור הצרכים של היום. שלב 2 נכנס רק כשיהיה טריגר מוצדק (מובייל/API). אין "big-bang", אין החלפה מסוכנת של כל מנגנון האימות בבת אחת.

9מה לא לעשות (Anti-patterns)

רשימת פסילה
  • אין לאחסן access/JWT ב־localStorage או sessionStorage.
  • אין להשתמש ב־HS256 עם סוד קצר; אין לקבל alg מהאסימון ללא allow-list; לדחות none.
  • אין אסימוני גישה ארוכי־טווח (שעות/ימים) בלי מנגנון ביטול.
  • אין לצרוב את כל מטריצת ההרשאות בתוך אסימון גלוי ללקוח.
  • אין להסתמך על localStorage.permissions בצד־לקוח כמקור סמכות — הוא רמז UI בלבד; הבדיקה הקובעת חייבת להישאר בשרת.

10קטעי קוד להמחשה

להמחשה בלבד — לא קוד לפרודקשן. מדגים עקרונות, לא מימוש סופי.

10.1 · אימות JWT מוקשח (אם נבחר JWT ולא PASETO)

# allow-list קשיח, דחיית none, אימות aud/iss, אלגוריתם א-סימטרי בלבד
import jwt
def verify_access(token, public_key):
    return jwt.decode(
        token, public_key,
        algorithms=["EdDSA"],        # רק EdDSA — לא HS*, לא none
        audience="childsmile-app",
        issuer="childsmile-auth",
        options={"require": ["exp", "iat", "sub", "sv"]},
    )

10.2 · Kill-switch באמצעות security_version

# מספר שלם אחד ב-Cache; אי-התאמה = דחייה מיידית של כל האסימונים הישנים
def is_token_current(claims):
    current_sv = cache.get(f"sv:{claims['sub']}")
    if current_sv is None:
        current_sv = Staff.objects.only("security_version") \
                        .get(pk=claims["sub"]).security_version
        cache.set(f"sv:{claims['sub']}", current_sv, 300)
    return claims["sv"] == current_sv   # bump ל-DB ⇒ פסילה מיידית

10.3 · המלצה א' — Cache להרשאות (המינימלי והמומלץ)

# מסיר את פניית ה-DB לכל בקשה, בלי אסימונים ובלי לאבד ביטול מיידי
def get_perms_cached(staff_id):
    key = f"perms:{staff_id}"
    perms = cache.get(key)
    if perms is None:
        perms = load_perms_from_db(staff_id)   # ה-JOIN הקיים
        cache.set(key, perms, 60)             # TTL קצר או פינוי בשינוי תפקיד
    return perms

11אופק עתידי — מעבר ל"טוב יותר מ־JWT" ברמת הארכיטקטורה

מכיוון שהתבקשתי "ללכת על זה" — הנה הכיוונים המתקדמים שמעבר לאסימונים גרידא, למקרה שמטריצת ההרשאות תמשיך לגדול (רכזים, Viewer, Reviewer, הרשאות חוצות־תחום):

Policy-as-Code

OPA/Rego או Cedar (AWS) מוציאים את החלטות ההרשאה מקוד היישום למנוע מדיניות ייעודי, בר־בדיקה ובר־אודיט. מתאים למערכת שבה הלוגיקה של "מי רשאי מה" מסתעפת.

אסימוני קפבילטי

Biscuit / Macaroons — אסימונים מבוססי־יכולת שניתן "לצמצם" (attenuate) עם caveats ולאמת offline. עוצמתי להאצלת הרשאות מדויקת, אך overkill להיום.

הערה

אלה מעבר להיקף הנוכחי — מובאים כדי להראות את מרחב הפתרונות המלא. אין צורך בהם כדי לפתור את בעיית העומס.

12שאלות פתוחות ל־ליאם (החלטות שדורשות שיקול אבטחה)

  1. האם צפוי בטווח הנראה לעין לקוח לא־דפדפני (מובייל / API לצד־שלישי) שבאמת מצדיק אסימונים חסרי־מצב? אם לא — המלצה א' מספיקה.
  2. מהו חלון ה־staleness המקובל להרשאות? (0 = חובה Sessions/Cache; דקות ספורות = Hybrid לגיטימי.)
  3. האם Redis זמין/מקובל כתשתית בפרוד (Azure)? זו התלות היחידה של המלצה א'.
  4. אם נלך על אסימונים — PASETO (ממליץ) או JWT א־סימטרי מוקשח? היכן יישבו מפתחות החתימה (Key Vault) ובאיזו מדיניות רוטציה?
  5. האם לאמץ DPoP / כבילת־שולח נגד replay, או שהסיכון לא מצדיק את המורכבות?
