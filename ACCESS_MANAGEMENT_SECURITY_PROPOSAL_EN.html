2The Django-admin backdoor — found live, already closed (PR #511)

Resolved ahead of the build — no longer part of the plan

Chasing your "coverage blind spots" point, we found childsmile_app/admin.py registering Role, Permissions, Staff (+ PII) with /admin/ routed — a full CRUD path around the firewall, TOTP, ADMIN_DEFINING, decorators and audit. A live prod check found one dormant superuser (amit_admin, last login 2025-10-12). So it was live, not hypothetical.

What shipped (PR #511)

(1) Disabled amit_admin in prod (is_active/is_staff/is_superuser = False) — the immediate key removed. (2) admin.py now registers no models and unregisters the built-in User/Group admin (broadly guarded so it can't break startup), so /admin/ exposes nothing and cannot mint a superuser; django.contrib.admin + the route are kept (OAuth-safe — /admin/ is nowhere in the allauth /accounts/ flow or the /#/google-success redirect). version.txt → 26.08.1.0. Verified: OAuth-created auth.Users are is_staff=False, and amit_admin was the only superuser.

Other blind spots checked: no websocket consumers; the 5 management commands are ops-CLI only (not user-reachable).

3Firewall — now code-constant, still binds admins

ADMIN_DEFINING (non-grantable) = any action on role, permissions, and staff CREATE/UPDATE/DELETE. Three layers: (L1) admin-defining surfaces stay is_admin name-based only; (L2) the set is non-grantable — save/create/rename hard-reject it for every caller incl. admins; (L3) is_admin name-based ⇒ a stray admin-defining perm is inert.

R2 #2 — the config that defines the firewall is itself immutable

ADMIN_DEFINING, RESERVED_ROLE_NAMES, and the is_admin role-name set are code constants deployed with the app — not readable or editable through any API, DB-config table, or admin screen. Changing them is a code deploy (covered by review + the CI guard). No runtime mutation surface = no meta-admin control to attack.

UX intact

Everything outside the set is grantable → an admin can build a "Finance Manager" custom role that reaches finance and nothing admin-defining.

4Migration safety — no shadow, no deny-by-default, and why that's OK here

Why DRF deny-by-default doesn't fit (R2 #1)

The app runs DRF with DEFAULT_AUTHENTICATION_CLASSES = [] and does its own session auth, so request.user is always AnonymousUser. A DRF IsAuthenticated/deny default would 403 every valid session. Making it work needs a custom DRF auth shim over the session (touches the auth path) — and it still wouldn't cover Django admin. So we address the actual risk directly.

Our three safety nets for the ~50-gate cutover:

1
Hardened Django admin (§2) — closes the real parallel mutation surface.
2
CI guard (deterministic, deploy-blocking) — presence + order + declared coverage. This, not "the AI won't forget", is what guarantees no gate is missed on the @api_view surface.
3
Negative per-gate tests — assert "unauthorized denied" as well as "intended allowed"; verify each (resource, action) mapping.

Decorators: @admin_only (name-based; admin-defining surfaces) and @admin_or_permission(resource, action) (everything else). Order: @conditional_csrf → @api_view → @admin_or_permission → @block_viewer_writes → def. Freshness (R2 #8) hangs off a generic permission-removed event so no removal path is missed.

5Reserved names, normalization, capabilities

Reserved names — now on the translation fields too (R2 #3)

Reject on create/rename against role_name and name_he/name_en — UI + backend, any caller. Blocks setting a custom role's Hebrew label to מנהל מערכת to impersonate the admin role.

Normalization (RN4)

NFKC + Unicode case-fold + trim/collapse-whitespace + strip bidi/RTL marks + strip Hebrew niqqud — applied identically to input, the reserved list, and the translations.

Capability seeding (R2 #6)

~5 grantable capability resources replace the coordinator name-lookups. Golden-master: capture today's routing per role, assert byte-identical after seeding. Seed before switching routing (same transaction, idempotent) so no notification window drops. Confirm pure-routing — none also gates a data read.

6Freshness — generic removal event (R2 #8)

The session-kill hangs off a single "permission-row-removed" event, so every removal path — screen save, capability revoke, role delete (CASCADE) — triggers it and none can be forgotten. Additions stay lazy (next login). No Redis, no security_version, no auth change.

7Two deliberate risk-acceptances — please sanity-check

No DB restore, ever (makes R2 #7 N/A)

The org will never run a DB restore, so we're not building one. Mitigations against a mistaken removal: per-cell explicit deltas (no accidental mass-delete), a confirm modal listing every removal, TOTP step-up, atomic apply, and an audit before-snapshot. Recovery = an admin re-checks the boxes via the screen using that snapshot — not a pg_restore. Acceptable?

No shadow phase; no DRF deny-by-default

Hard all-or-nothing cutover. We rely on the deterministic CI guard (order + coverage) + negative tests + the Django-admin fix, rather than a shadow-log period or a framework default that doesn't fit our auth. Is that residual risk acceptable given the guard is deploy-blocking and the real parallel surface is closed?
